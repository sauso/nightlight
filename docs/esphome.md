# ESPHome data collection

Nightlight can connect directly to an ESPHome device through its Native API and collect its numeric and binary sensor updates. This first version is for collecting data to see whether it is useful. It does not show a chart or send an alert, and it changes no sleep time, figure or notification. The one thing sleep tracking does with the readings is store a second, sensor-based wake time beside each night, **for comparison only** (see [The sleep shadow](#the-sleep-shadow-for-comparison-only)). It does not connect through Home Assistant or discover devices on the network.

An admin adds and manages devices in **Settings → Integrations → ESPHome** (described [below](#the-settings-screen)). The server connects to the device's IP address on port **6053** by default. Give the device a fixed IP address and use that address; names ending in `.local` do not resolve inside the container. Up to **8 devices** and **200 discovered entities per device** are supported. Only numeric `sensor` and `binary_sensor` entities are recorded. Diagnostic and disabled entities are skipped. Other kinds, including lights and switches, are ignored. ESPHome builds an entity's id from its name, so two names such as "Temp 1" and "Temp.1" can end up with the same id; only the first of them is recorded, and the log notes `duplicate entity id ignored` once for that device. Two entities of different kinds with the same name, such as a binary sensor and a sensor both called "Presence", share one key on the device, and their updates cannot be told apart. Neither of them is recorded, and the log notes `entity id shared by two kinds, ignored` once for that device. To record both, give one of them another name in the device's configuration. Nightlight sends no control instructions to the device.

Everything the screen does is also available to scripts through the API. With an admin session, `POST /api/esphome/devices` accepts `name` (your own label), `host`, optional `port`, optional `key`, optional `child_id`, and `enabled`. `GET /api/esphome/devices` shows connection and collection status; `GET /api/esphome/devices/<id>/entities` shows discovered entities and their latest live values. `PUT /api/esphome/devices/<id>` changes a device; `DELETE` at the same address removes its history. `POST /api/esphome/test` checks a `host`, optional `port` and `key`, or an existing `device_id`, without storing readings. Only one test runs at a time, for at most 10 seconds.

If the device uses Native API encryption, find its key in the device's YAML configuration or `secrets.yaml`, under `api: encryption: key:`. Paste the base64 key when adding the device. A blank key field when editing keeps the stored key; `clear_key: true` removes it. The key is never returned by the API. When a key is set, Nightlight refuses a connection unless the client confirms that it is encrypted. Without a key, a plaintext connection is allowed. **Plaintext traffic can be read on the network**; use it only on a network you trust. As with MQTT and cameras, an admin can point the server at any host and port.

## The settings screen

**Settings → Integrations → ESPHome**, for admins. Its row in the Integrations list carries a badge: **Connected** when every enabled device is connected, **Disconnected** when an enabled device is not, **Off** when there are no devices or all of them are switched off.

- **Each device** shows its connection state (**Connected**, **Connecting**, **Disconnected** for a connection that dropped and is being retried, **Failed**, or **Off** for a device you switched off), its address, the child it is assigned to, when its last reading was stored, how many readings were stored in the last hour, and how many sensors it has. When a connection fails, a short fixed sentence says why where Nightlight knows (for example that the key was rejected). The screen refreshes every 10 seconds while it is open, and not while the tab is hidden.
- **Encryption.** A connected device shows **Encrypted**, or a warning that anyone on your network can read its readings if the connection is not encrypted. A device that is not connected shows whether a key is set instead, because whether the connection is encrypted is only known once it is connected.
- **Add or edit** a device: your own label for it, its IP address, an optional port (default 6053), an optional encryption key, the child it belongs to, and a switch to stop or start collecting. At most **8** devices. The key is never shown again after you save it, and the screen does not keep it anywhere in the browser. Leave the key blank when editing to keep the stored one, or tick **Remove the stored key**. Typing a new key replaces it. **Test connection** in the add form checks what you have typed before you save it.
- **Test** on a saved device connects once and stores nothing (at most 10 seconds, one test at a time) and says whether the connection is encrypted and how many sensors it found. **Sensors** lists what the device reported with the latest value and its age.
- **Delete** removes the device and **all the readings stored for it**, after a confirmation.
- **Keeping readings:** **30 days** by default, any whole number from **1 to 365**; older readings are deleted automatically. The sensor-based wake stored with each night ([below](#the-sleep-shadow-for-comparison-only)) is kept with the night, not with the readings, so it outlives this setting; keep the readings longer if you want to recheck a night from them later.
- **Download CSV:** see the next section.

## What is stored

For each active entity, Nightlight combines the minute's updates into one UTC minute row. `last` is the last valid value in that minute, including a zero. For a numeric sensor, `mean`, `min` and `max` describe the valid values other than zero, `n` counts them, and `nzero` counts the updates that were exactly 0 (see below). `nmiss` counts only the updates the device itself flagged as having no valid reading (or sent as not-a-number), for numeric and binary sensors alike. A missing update, including a zero with the missing flag, never becomes a value and is not counted in `nzero`. A numeric sensor that sends only zeros or missing updates in a minute gets a row with `n = 0` and no `mean`, `min` or `max`; its `last` is 0 if a zero came in, and empty if only missing updates did. A numeric sensor that sends nothing has no row: the gap means unknown.

A device leaves a zero, or a binary "off", out of its update. Nightlight records such an update as **0**, a real reading, not a missing one. On the sensors this was built for, **a heart rate or breathing rate of 0 usually means "no reading"** rather than a measured zero, and over a night most heart-rate updates can be zeros. So for a numeric sensor Nightlight counts zeros separately, in `nzero`, and keeps `mean`, `min`, `max` and `n` for the readings that were not zero. For example, a minute with 4 updates of 70 bpm and 6 zeros is stored as `mean` 70, `min` 70, `max` 70, `n` 4 and `nzero` 6, with `last` 0 if the minute ended on a zero.

Nothing is lost. Where 0 is an ordinary value, such as 0 lx in a dark room, a target count of 0 when nobody is detected, or a temperature of 0 °C, rebuild the overall figures for a minute from the row: all its readings number `n + nzero`, the overall mean is `mean × n / (n + nzero)` (0 when `n` is 0), and the overall minimum is 0 whenever `nzero` is more than 0. Some devices also send a respiratory rate of **1.0** as a placeholder; Nightlight stores it as sent, as an ordinary reading. For a binary sensor, 0 ("off") is data: it counts in `n`, `mean` is the fraction of updates that were on, and `nzero` is always 0.

A binary sensor carries its last known 0 or 1 into later minutes while the device stays connected. Such a row has `n = 0`; its `nmiss` counts any missing updates in that minute, and a missing update does not clear the carried value. A binary sensor that sends only missing updates and has no earlier value gets a row with `n = 0`, `nmiss > 0` and no value. A disconnect clears the last known value; no rows are carried across it. The device's presence flag is stored as reported, even if it changes often or stays on after someone leaves. The values are **reported by the sensor, not interpreted by Nightlight, not a medical measurement**. Nightlight is not a medical or safety device.

If the server is paused for a minute or more (for example the process is suspended), it leaves a gap rather than guessing what happened during the pause. Up to about two minutes around a disconnect or restart are not recorded: the minute in progress and the one waiting to be written are held in memory only.

The default retention is **30 days**, adjustable from **1 to 365 days** on the settings screen or through `/api/esphome/settings`. Old minute rows are pruned in batches. Deleting a device deletes its readings; deleting a child deletes readings attributed to that child. Moving a device to another child leaves earlier readings attributed to the previous child. An admin can download up to **31 days** at a time as CSV from `/api/esphome/export?device=<id>&from=<ISO>&to=<ISO>`. `from` and `to` are ISO dates or date-times; a time without a `Z` or an offset is read as UTC (write a `+` offset as `%2B` in the address). The file's columns are `minute_utc,device,entity,child,last,mean,min,max,n,nzero,nmiss`, as described above; `device` is the device's number, such as `#3`, not its name. Times in the file are UTC with a `Z` suffix. A name or child id that starts with `=`, `+`, `-` or `@` gets a leading `'` so a spreadsheet does not run it as a formula; numbers, including negative ones, are written as they are.

On the settings screen, **Download CSV** gives the same file for a From and a To date. They are **UTC days**, the To day is included, and the times in the file are UTC, so nothing depends on the timezone of the server or the phone. The screen holds the whole file in memory, so it refuses a range it estimates at more than about **25 MB**, counting one row per sensor per minute at about 75 bytes a row (an estimate from the sensors the device has now, not a measurement; readings of sensors it no longer reports are not counted). A device with the usual handful of sensors can be downloaded for the full 31 days; a device with 200 sensors is limited to one day. The API itself does not limit the number of rows, so a script can ask for more. The screen saves the file as a normal download in a browser, and into the Downloads folder in the Android app (an old app version that cannot save files says to update).

While a device is connected, each of its entities writes about one row a minute (a minute of only zeros is a row too). A device with 5 numeric entities and 1 binary one writes roughly **8,600 rows per day**, about **0.4 MB per day**. This is an estimate, not a capacity guarantee: it has not been measured against the current behaviour. The database and its backups contain the raw readings and the stored encryption key; protect the data directory.

## The sleep shadow (for comparison only)

A camera sometimes logs a child as getting out of bed when they only turned over, and the morning wake time then comes out too early. A radar sensor at the bed can see whether a person's heartbeat or breathing is still there after that *got out of bed*. Nightlight now works out, beside each night, **the wake time it would have reported if it had listened to the sensor**, and stores it. **It changes nothing you see**: not the wake time, any other figure, the morning notification or an alert. It is evidence, collected so the idea can be checked on real nights before it is ever allowed to act.

**Why it does not act yet.** The sensor cannot tell a child from an adult. If a parent stands at the bed within a few minutes of a child really getting up, the sensor reads their heartbeat, and the rule then wrongly sets the real *got out of bed* aside. In a test that added a parent's readings for six minutes shortly after the real wake on six recorded mornings, the sensor-based wake moved 56 to 91 minutes later on four of them. Until that case is understood, the sensor only shadows the real answer.

**When it runs.** For a child whose ESPHome device reports a heart rate or a breathing rate, on every finished night (not the night in progress) that has those readings. Nightlight recognises the two by the sensor's name: "heart rate", and "respiratory rate", "respiration rate" or "breath rate" (with or without a space or underscore). A sensor named anything else ("Breathing rate", "Pulse", "HR" or a name in another language) is not used. A child with no such sensor is worked out exactly as before.

**The rule.** A camera *got out of bed* is set aside when the sensor measured a person in at least **6 of the 10 minutes after it** (the minute of the exit itself is not counted). A minute counts when, from one device, the heart rate had at least **3** readings that were not zero, or the breathing rate at least **30** (a breathing rate under **2** is the placeholder some sensors send, not a breath), and that device's distance reading was **1 m or less**. The distance must be in `cm`, `m` or `mm`; any other unit, or none, means the minute does not count. A minute with no distance reading at all is not held back by it. A minute with no readings at all (the device was off or disconnected) never counts. An exit set aside this way is treated like the existing "climbed straight back in" check: a later *got out of bed* can take its place, and if none does, it is used after all, so this never leaves a night without a wake time. These numbers are **fixed, not settings**.

**Where it is stored.** Two columns of the night's saved row, also added to the night's API answers: `wake_at_sensor`, the sensor-based wake time (UTC, like `wake_at`), and `sensor_rejects`, how many *got out of bed* events the sensor set aside. Both are empty (`null`) when the night had no heart-rate or breathing readings when it was saved, and on nights saved before this. A night whose wake time you corrected in the morning review, or marked "no one was in the bed", shows both as empty (a correction of only the in-bed or asleep time leaves them); its saved row keeps them.

**Reading the evidence.** An admin with database access can compare the three answers, the camera's, the sensor's and yours from the morning review (times are UTC):

```sql
SELECT n.night_date, n.wake_at, n.wake_at_sensor, n.sensor_rejects, r.true_wake_at
  FROM sleep_nights n
  LEFT JOIN sleep_reviews r ON r.child_id = n.child_id AND r.night_date = n.night_date
 WHERE n.sensor_rejects IS NOT NULL
 ORDER BY n.child_id, n.night_date;
```

Before the sensor is allowed to change a wake time, it should be right on **at least 15 reviewed nights**, including **at least 5 where an adult was at the bed within minutes of a real wake**, and make **none** of them worse.

**Limits, all of them known:**

- **Measured in one house:** two children, one sensor each, three reviewed nights. On those nights the real wakes had 0 to 2 minutes with a person measured in the 10 minutes after the exit, and the false ones 9 or 10, so the line of 6 sat clear of both, and the rule moved two wake times to the time the parent saw (they had been 25 and 38 minutes early). Both were the same child and the same sensor. The other sensor read only zeros for long stretches (once for over three hours) while the child was in bed: on such a sensor the rule simply sets nothing aside.
- **The 1 m distance limit is weak.** After most of the real wakes the distance read a steady 57 to 75 cm over the empty bed, so it would not have kept an adult's heartbeat out. Only the reading counts tell the two apart.
- **It assumes the sensor reports several times a minute**, as the ones it was measured on did. A device set to report once a minute never reaches 3 or 30 readings, and sets nothing aside.
- **The sensor-based time can change during the morning.** An exit set aside early in the morning can be used after all while nothing later qualifies, then lose to a later *got out of bed* once that one has 20 quiet minutes after it.
- **It is computed from the readings there at that moment.** The saved value is whatever the last save of the night saw. A night is saved again until about 3 hours after its window ends (and when an admin re-works it out), so readings that arrive late are picked up within that time, and a night re-worked out after its readings were deleted saves an empty value. A night that was already final, or locked by a correction, before its readings existed never gets one. A fresh look at an old night (the sleep detail page) reads the readings that are left, so it can differ from the saved row; don't treat either as the wake time Nightlight reports.
