# ESPHome data collection

Nightlight can connect directly to an ESPHome device through its Native API and collect its numeric and binary sensor updates. This first version is for collecting data to see whether it is useful. It does not show a chart, send an alert, or use the data in sleep tracking or any other computed number. It does not connect through Home Assistant or discover devices on the network.

An admin can configure a device through `/api/esphome` until the settings screen is added. The server connects to the device's IP address on port **6053** by default. Give the device a fixed IP address and use that address; names ending in `.local` do not resolve inside the container. Up to **8 devices** and **200 discovered entities per device** are supported. Only numeric `sensor` and `binary_sensor` entities are recorded. Diagnostic and disabled entities are skipped. Other kinds, including lights and switches, are ignored. ESPHome builds an entity's id from its name, so two names such as "Temp 1" and "Temp.1" can end up with the same id; only the first of them is recorded, and the log notes `duplicate entity id ignored` once for that device. Nightlight sends no control instructions to the device.

With an admin session, `POST /api/esphome/devices` accepts `name` (your own label), `host`, optional `port`, optional `key`, optional `child_id`, and `enabled`. `GET /api/esphome/devices` shows connection and collection status; `GET /api/esphome/devices/<id>/entities` shows discovered entities and their latest live values. `PUT /api/esphome/devices/<id>` changes a device; `DELETE` at the same address removes its history. `POST /api/esphome/test` checks a `host`, optional `port` and `key`, or an existing `device_id`, without storing readings. Only one test runs at a time, for at most 10 seconds.

If the device uses Native API encryption, find its key in the device's YAML configuration or `secrets.yaml`, under `api: encryption: key:`. Paste the base64 key when adding the device. A blank key field when editing keeps the stored key; `clear_key: true` removes it. The key is never returned by the API. When a key is set, Nightlight refuses a connection unless the client confirms that it is encrypted. Without a key, a plaintext connection is allowed. **Plaintext traffic can be read on the network**; use it only on a network you trust. As with MQTT and cameras, an admin can point the server at any host and port.

## What is stored

For each active entity, Nightlight combines valid updates into a UTC minute row. `last` is the last valid value in that minute; `mean`, `min` and `max` describe the valid values; `n` counts them. `nmiss` counts only the updates the device itself flagged as having no valid reading (or sent as not-a-number), for numeric and binary sensors alike. A missing update, including a zero with the missing flag, never becomes a value. A numeric sensor that sends only missing updates gets a row with `n = 0`, `nmiss > 0` and no value. A numeric sensor that sends nothing has no row: the gap means unknown.

A device leaves a zero, or a binary "off", out of its update. Nightlight records such an update as **0**, a real reading, not a missing one. **A heart rate or breathing rate of 0 is stored raw**, and on these sensors it usually means "no reading" rather than a measured zero. The same goes for a respiratory rate of **1.0**, which some devices send as a placeholder.

A binary sensor carries its last known 0 or 1 into later minutes while the device stays connected. Such a row has `n = 0`; its `nmiss` counts any missing updates in that minute, and a missing update does not clear the carried value. A binary sensor that sends only missing updates and has no earlier value gets a row with `n = 0`, `nmiss > 0` and no value. A disconnect clears the last known value; no rows are carried across it. The device's presence flag is stored as reported, even if it changes often or stays on after someone leaves. The values are **reported by the sensor, not interpreted by Nightlight, not a medical measurement**. Nightlight is not a medical or safety device.

If the server is paused for a minute or more (for example the process is suspended), it leaves a gap rather than guessing what happened during the pause. Up to about two minutes around a disconnect or restart are not recorded: the minute in progress and the one waiting to be written are held in memory only.

The default retention is **30 days**, adjustable from **1 to 365 days** through `/api/esphome/settings`. Old minute rows are pruned in batches. Deleting a device deletes its readings; deleting a child deletes readings attributed to that child. Moving a device to another child leaves earlier readings attributed to the previous child. An admin can download up to **31 days** at a time as CSV from `/api/esphome/export?device=<id>&from=<ISO>&to=<ISO>`. `from` and `to` are ISO dates or date-times; a time without a `Z` or an offset is read as UTC (write a `+` offset as `%2B` in the address). Times in the file are UTC with a `Z` suffix. A name or child id that starts with `=`, `+`, `-` or `@` gets a leading `'` so a spreadsheet does not run it as a formula; numbers, including negative ones, are written as they are.

While a device is connected, each of its entities writes about one row a minute (a zero reading is a row too). A device with 5 numeric entities and 1 binary one writes roughly **8,600 rows per day**, about **0.4 MB per day**. This is an estimate, not a capacity guarantee: it has not been measured against the current behaviour. The database and its backups contain the raw readings and the stored encryption key; protect the data directory.
